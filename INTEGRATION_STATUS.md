# INTEGRATION_STATUS.md — every external integration, one status each (mandate §244 / 130-section §124), updated Oct 26 2026

## Oct 26 2026 — what changed since Oct 22

- **Tap to Pay (Fiserv CommerceHub):** still **BLOCKED_EXTERNAL** for the real charge. The device-authentication layer around it is complete (M6 + Oct 26):
  - signed requests per phone (P-256, migration 687)
  - pairing, approve and revoke behind step-up
  - shared phones (688)
  - refresh families (689)
  - claim version / `CHECKOUT_STALE` (690)
  - `/reconcile` asks the provider and never takes the phone's word
  - attestation intake (`POST /mobile-checkout/device/attest`, `TTP_ATTESTATION_POLICY`)
  - store switch refused with `MERCHANT_NOT_CONFIGURED` when the target location has no active merchant

  Two findings:
  - **Single MID for all locations:** the CommerceHub charge uses ONE platform merchant, `COMMERCEHUB_TTP_MERCHANT_ID` from the environment, for every location and every salon. The per-location merchant account (CardPointe / `PaymentGatewayResolver`) is recorded on the intent and the payment, and reports follow it (pilot S14). The store-switch merchant check reads that resolver, not CommerceHub. Per-location CommerceHub MIDs need Fiserv onboarding per location and a code change to pick the MID per location.
  - **Inquiry lookup needs the sandbox:** `lookupTransaction` in `fiserv-commercehub-ttp.adapter.ts` answers `no_inquiry` until `inquireByOrderId` is implemented and verified against CommerceHub sandbox credentials. Until then an unknown phone payment stays "verifying" and a person resolves it, which is pilot S8 (INFO BLOCKED_EXTERNAL). Nothing fakes success.
- **CardPointe:** no change. SANDBOX_READY, with live MIDs + UAT pending (Kevin). Recovery for top-ups (679), Skip-the-Line (680) and split cards is built on `inquireByOrderid` (Oct 23). The wallet **webhook** leg is not wired yet (NEXT_STEPS I-3). B-23 (refund listing shape) still needs UAT.
- **Twilio / SendGrid / Firebase + APNs:** no change. These are built and blocked on accounts and keys (Kevin). Firebase needs a NEW service account, because the old exposed key is revoked in K-12 step 3.
- **S3 / ClamAV / Textract:** no change. Without them, uploads are honestly quarantined. Since Oct 26, a `MALWARE` / `SCAN_UNAVAILABLE` refusal raises a `security_signal` alert (§153). Still internal: unscanned *images* are not quarantined yet (Security §104 / §106).
- **Redis:** now also backs the **per-IP anonymous limiter** (`@AnonRateLimit`, Oct 26). Its store is `RATE_LIMIT_REDIS_URL` / `REDIS_URL` with `RATE_LIMIT_STORE` ≠ `memory`; it fails open on a Redis error and runs in-process without Redis. With more than one API replica, Redis is required for shared counts (tenant limiter, login throttle, anonymous limiter, realtime fan-out).
