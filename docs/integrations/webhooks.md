# Provider webhooks — every inbound callback and how it is secured (§44–§46, §70, §87, §157–§158)

All provider callbacks live under `/api/v1/webhooks/...` on dedicated, **unauthenticated-by-design** routes (listed in
`unguarded-route-check`'s PUBLIC_BY_DESIGN) — never behind a tenant session, never trusting a tenant id in the body.
Every one performs, in order: provider authentication (signature over the exact raw bytes — `NestFactory({ rawBody: true })`,
`PAYMENTS_WEBHOOK_RAW_BODY=1` mandatory in production), freshness / replay checks where the provider gives a timestamp,
**provider-account → tenant resolution from OUR configuration**, deduplication, schema validation (`ValidatedBody`),
event storage, then business processing. A forged or corrupt signature is a `WEBHOOK_SIGNATURE_FAILED` security event.

| Route | Provider | Authentication | Tenant resolution | Dedupe | Storage | Effects |
|---|---|---|---|---|---|---|
| `POST /webhooks/payments/:processor` (`fiserv`, `cardpointe`, `clover`) | card processor | HMAC-SHA256 hex over raw body with **the resolved tenant's own `webhook_secret`** (`x-webhook-signature` / `x-cardpointe-signature`, `sha256=` prefix tolerated) | merchant id in the payload → exactly one row across `tenant_payment_config` + `payment_merchant_accounts`; unknown/ambiguous → 400 `unknown_merchant` (recorded, signature_valid=false) | `uq_payment_gateway_events_tenant_processed (tenant, processor, event_id) WHERE processed_at IS NOT NULL` — the claim row is written BEFORE any effect; a concurrent duplicate loses the race and answers `duplicate`; money keys (refund id, settlement id, chargeback case) are unique per tenant too | `payment_gateway_events` (safe payload, no card data; `processing_attempts`, `last_error`) | payment status through the PAYMENT machine (a late `settled` never overwrites `refunded`), `payment_refunds`, `payment_settlements` (+ payment links), `chargebacks`, merchant onboarding status. **Processing failure after the claim** (§45): the row keeps the error + attempt count and releases its claim; the processor gets **500 `processing_failed`** and its retry reprocesses once (`payment-webhook-inbox-failure.pgtest`). |
| `POST /webhooks/bank/:token` | bank / deposit feed | per-endpoint token in the path + HMAC signature + timestamp tolerance (replay) over raw body | the endpoint token → tenant bank account | external transaction id unique | `bank_deposits` | deposit reconciliation |
| `POST /webhooks/twilio/sms/inbound` | Twilio | `X-Twilio-Signature` (HMAC-SHA1 over URL + sorted params) with the auth token of the account that owns the number (`AccountSid` → tenant credentials, else the platform token) | the `To` number → `tenant_messaging_numbers` (one salon per number) | Twilio MessageSid (`twilio-webhook-dedupe.pgtest`) | `inbound_messages` (safe text) | STOP/START/HELP keyword handling → `notification_opt_outs`; otherwise the communications inbox |
| `POST /webhooks/twilio/sms/status` | Twilio | same signature scheme | MessageSid → `notifications.provider_id` (globally unique) | status machine (NOTIFICATION) — a late callback never moves `delivered` back | `notifications`: status, `delivered_at`, `provider_status`, `provider_error_code`, `segment_count` | `communication.sms_delivery_failed` once per row that moves into failed |
| `POST /webhooks/twilio/booking-verification/status` | Twilio Verify | signature verified with **the candidate tenant's own token first** (the tenant is never taken from the body) | verification SID → booking verification session | session state machine | verification session | OTP delivery status |

## Observability (§158)

`aipowersalon_webhook_events_total{provider,outcome}` with outcomes `received / verified / rejected / duplicate / processed /
failed`, plus `aipowersalon_webhook_latency_ms{provider}` (histogram) and this process's last/max latency in
`webhookCounts()` → System Operations and `/metrics`. Super Admin → tenant → **Webhook events** shows recent deliveries with
their signature verdict and a health summary (`healthy` / `failing` / `none yet`).

## Secrets and rotation (§97–§99)

Payment webhook secrets are generated by AIPowerSalon (`whsec_…`, 24 random bytes), sealed with the PAYMENT key, shown
**once** on rotation (Super Admin → Rotate webhook secret, audited `payment_gateway_webhook_secret_rotated`) and pasted
into the processor's dashboard. Twilio signatures use the account auth token already sealed in `tenant_messaging_credentials`
(PROVIDER key) or the platform token in env. Bank endpoint tokens are per bank account. Nothing in this table is ever
returned to a client after creation.

## DR (§181–§183)

After a database restore, do not replay webhook payloads blindly: the inbox rows are the evidence of what arrived; run
deposit reconciliation and the payment-attempt sweep (they ask the processor) and compare `payment_gateway_events` with
the processor portal for the restore window. Twilio messages after the restore point are visible in the Twilio console;
the status callback for them will simply find no row (`updated: 0`) — no duplicate sends happen from a callback.
