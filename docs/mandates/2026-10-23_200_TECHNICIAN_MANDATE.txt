1. Primary product goal
AI PowerSalon must support a large salon or tenant with 200 technicians without Booking, Tech Queue, Fair Turn, Team,
Technician App, payroll, realtime or backend APIs becoming slow or unstable.


2. Do not hard-code 200
200 is the required certification/stress target, not the architectural maximum. Design for 300, 500 and 1,000+ technicians
without another rewrite.


3. Audit existing technician limits
Search for hard-coded 12/24/50/100/200 assumptions, maxTechnicians, pageSize, slices and SQL LIMITs. The earlier pilot
already exposed hidden record limits, so treat this as a formal defect class.


4. Booking board pagination
Keep 12 visible technicians per page. For 200 technicians the system must report page 1 = 1-12, page 16 = 181-192, page 17 = 193-
200.


5. Pagination controls
Support First, Previous, Next 12, Last and Page X of 17. Direct page selection is optional if it fits the current design.


6. Preserve existing booking design
Keep Day/Week/Today, date navigation, 15-minute grid, Find an Opening, Best Matches, filters, Working Technicians, 12 per
page, Fit Day, Full Screen, Add Walk-In, New Booking, Print Schedule and Block Time.


7. Never render all 200 columns
Do not create 200 technician columns in the DOM and hide 188 with CSS. Only render the active 12 plus minimal navigation
metadata.


8. Server-side technician paging
Backend must page technicians using trusted tenant/branch context and return total/pageSize/page/totalPages or cursor
equivalents.

 GET /booking/technicians
  trusted tenant/branch
  date
  pageSize=12
  page/cursor
  filters


 Response concept:
 technicians[]
 total=200
 pageSize=12
 page=1
 totalPages=17




9. Never trust tenant or branch from client
Resolve scope from authenticated employee context. Client pagination must never permit cross-tenant browsing by modifying
tenantId.

16. Best Matches at scale
Filter hard eligibility first, then rank. Ineligible technicians must never enter the ranking stage.


17. Candidate result limit
Best Matches may return top 5 or top 10 plus View More rather than 200 results.


18. Appointment queries for visible technicians
For a 12-tech page, fetch the date range and visible technician IDs rather than every appointment for all 200 staff.


19. Adjacent-page prefetch
Optionally prefetch the next page after the current page stabilizes; do not prefetch all 17 pages.


20. Safe booking cache keys
Cache keys must include tenant, branch, date, service/status/working filters and page/cursor to prevent leakage and stale
collisions.


21. Realtime with 200 technicians
Avoid 200 unnecessary individual subscriptions. Prefer authorized branch/date/resource projections and invalidate/refetch
only affected visible data.


22. Off-screen realtime changes
Changes to technician #150 while viewing page 1 should invalidate relevant off-screen cache/metadata, not rerender page 1.


23. Page navigation state preservation
Preserve date, Day/Week mode, service/status/working filters, Fit Day and time scroll where practical across page changes.


24. Booking performance targets
Measure real latency. Suggested initial targets: normal initial load <2s; cached/prefetched page change ~500-750ms perceived;
filter change typically <1s; moves give immediate feedback and fast server confirmation.


25. Database index audit
Inspect indexes for tenant_id, branch_id, technician_id, employment status, schedule date, appointment date/time, service_id
and technician-service skills. Use EXPLAIN/EXPLAIN ANALYZE before adding indexes blindly.


26. Avoid N+1 queries
Do not execute 200 schedule + 200 appointment + 200 skill queries. Batch/aggregate data for visible pages and server-side
search.


27. Lightweight technician summary projection
Booking payload should return id, display name, thumbnail, working/status summary, selected-service eligibility and next-
opening metadata where needed - never payroll/private notes/tax data.


28. Availability strip efficiency
Calculate only useful openings for currently visible technicians, not their entire future calendars.
