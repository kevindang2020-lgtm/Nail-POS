10. Dependency Direction
Apps may consume API contracts, SDKs, and UI packages. Business modules own domain rules. Infrastructure
packages implement cross-cutting concerns.
Never allow:
  React Component -> PostgreSQL
  Technician App -> Kysely
  Appointment Module -> Twilio directly
  Checkout Module -> Clover SDK directly
  Queue Module -> socket room directly
  AI Module -> unrestricted SQL

11. Trusted Request Context
Every authenticated request must create a trusted server context. Conceptually:
  RequestContext {
    requestId
    correlationId
    identityId
    authRealm
    tenantId?
    branchId?
    roles[]
    permissions[]
    scopes[]
    deviceId?
    sessionId
  }

Tenant and branch authorization must never depend only on req.body.tenantId, req.query.tenantId, or frontend
localStorage.

12. Multi-Tenant Isolation
Every tenant-owned business entity must be tied to trusted tenant context. Tenant A must never access Tenant B
customers, appointments, employees, payments, payroll, merchant account, Twilio, advertising, or reports.

13. Branch Isolation
Branch-scoped resources must include branch_id where applicable, including appointments, queues, terminals,
technician shifts, merchant accounts, inventory, customer displays, and advertising.

14. Tenant-Aware Database Integrity
Use database constraints wherever possible. Do not depend only on application queries to prevent cross-tenant
associations. An Appointment for Tenant A must not reference a Technician from Tenant B even if a bug bypasses
service validation.

15. Identity Architecture
Separate GLOBAL IDENTITY from TENANT MEMBERSHIP. A user may belong to multiple tenants/branches.

16. Authentication Realms
Maintain separate authentication domains:
  EMPLOYEE
  PLATFORM
  CUSTOMER
  PUBLIC_BOOKING
  SERVICE
  INTEGRATION

Do not create a universal token usable everywhere.

17. Employee Authentication
Support existing implemented methods such as email/password, phone OTP, passkey, MFA, trusted device, and
device biometric unlock depending on real code.

18. Face ID / Touch ID
Biometrics unlock a device-bound credential. The backend must never store Face ID templates or Touch ID
fingerprint templates.

19. Sessions
Use short-lived access tokens, rotating refresh tokens, refresh-token families, reuse detection, session records,
device trust, and revocation where already implemented.

20. Employment Termination
When employment ends, revoke tenant sessions, refresh tokens, device access, permission cache, and realtime
connections. Professional/global identity may remain.

21. Authorization Model
Use:
  RBAC + RESOURCE SCOPE + POLICY CONDITIONS

Deny by default.

22. Tenant Roles
Possible built-ins include Owner, Admin, Manager, Receptionist, Technician, Accounting, Inventory, and
Marketing plus custom roles.

23. Platform Roles
Super Admin roles are separate from tenant roles. A platform role must not automatically become Salon Owner
inside every tenant.

24. Permission Scopes
Support OWN, ASSIGNED, BRANCH, SELECTED_BRANCHES, TENANT, and PLATFORM.

25. Field-Level Authorization
Even if a user may view Technician Profile, that does not mean they may see commission, payroll, private notes,
or tax information. Use separate DTO projections.

26. Feature Entitlement Is Not Permission
Separate Plan allows feature from User has permission. Both may be required.

27. API Architecture
Use versioned domain APIs under /api/v1 and separate tenant, customer, public booking, platform, webhooks,
integrations, and internal namespaces where appropriate.

28. Standard API Envelope
Normalize success, data, meta, requestId and a standard error structure.

29. Runtime Validation
All mutation DTOs require strict runtime validation. No mass assignment.

30. Pagination
Use cursor pagination for large datasets. Avoid SELECT every customer for normal pages.

31. Idempotency
Critical mutations require idempotency, including payment, refund, check-in, appointment creation, gift-card
redemption, payroll adjustment, and queue assignment.

32. Optimistic Concurrency
Use resource versions for appointment, customer, schedule, queue, checkout, inventory, payroll, and membership
where simultaneous edits matter.

33. Money
Permanent rule:
  NO FLOATING-POINT MONEY

Use integer minor units or the existing precise NUMERIC convention consistently.

34. Dates and Time
Use UTC for stored timestamps where appropriate plus tenant/branch timezone for business interpretation.
Handle DST, business day, pay periods, appointments, and reports correctly.

35. Event Architecture
Events mean something happened, not please do this. Keep commands/jobs separate.

36. Event Envelope

  eventType
  eventVersion

37. Transactional Outbox
Critical domain mutation plus Outbox Event must commit in the same transaction. Workers/event dispatcher
publish later.

38. Delivery Semantics
Assume AT-LEAST-ONCE DELIVERY. Consumers must be idempotent.

39. Consumer Deduplication
Persist processed-event keys for critical financial and side-effect consumers.

40. Dead-Letter Handling
Workers need retry, backoff, jitter, DLQ, and manual replay.
