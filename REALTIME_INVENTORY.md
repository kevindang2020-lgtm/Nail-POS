## 1. The one path (Constitution 9)

```
domain write (business transaction) ──▶ outbox_events          [packages/events writer, same transaction]
   ──▶ outbox-publisher (worker tick) ──▶ consumer-runner        [apps/api/src/events]
        ──▶ 10 consumers (below)  ──▶ realtime-projection.consumer ──▶ realtime-bus ──▶ SSE stream (r0/r1)
                                                                       └▶ Redis fan-out when >1 replica
clients: @aipowersalon/realtime-client — frame {event, v, screens, payload, seq, stream}; the screens named REFETCH their
own snapshot API (realtime never introduces a second read path); gap in seq → resync (/realtime/resync).
```

- **Projection map**: `realtime-projection.consumer.ts` — **108 domain → client mappings** (approval, authorization, booking, check-in, queue, serving, checkout/payments (`checkout.completed`, `payment.captured`, `payment.failed`, ticket ready), cash drawer / hand-off, display, technicians, owner alerts, community, schedule optimizer, AI queue assignment, settings, tenant status, platform ops).
- **Direct emissions outside the projection** (ratcheted, `tooling/architecture-tests/baseline.json` `moduleDirectEmissions`): **0** (Oct 20 2026, B-14 `51c3f827` + `331b5b67`). Every former direct push — Booking "Start service", the kiosk check-in, tech-profile salon-wide facts, and all eleven queue-assignment facts — is a recorded domain event the projection delivers; the services' own pushes remain only as the publisher-off fallback, each deciding through `projectionDeliversRealtime`.

## 2. Channels (§248) — who may subscribe, scope, internal room

| Channel | Actors | Permission | Scope | Snapshot API the client refetches |
|---|---|---|---|---|
| `branch.queue` | tenant staff | `pos.login` | branch (from session) | `GET /pos/queue`, `/pos/check-in` |
| `branch.booking` | tenant staff | `pos.login` | branch | `GET /pos/booking` (board range) |
| `branch.serving` | staff; ticket holder (Customer App) for ticket events | `pos.login` · ticket holder | branch / ticket | `/pos/serving`, `/pos/service-done` |
| `branch.checkout` | tenant staff | `pos.login` | branch | `/pos/checkout/tickets/:id` (incl. `refunds/unsettled`) |
| `technician.me` | technician (self) | technician session | self + home branch | `/tech/*` |
| `owner.dashboard` | owner | owner session | tenant (+ home branch) | `/owner/*` |
| `customer.me` | customer (self) | customer session | self + checked-in branch | `/customer/me` |
| `platform.live-ops` | SUPER_ADMIN | `SuperAdminGuard` | platform aggregates | `/super-admin/system-status/realtime` |
| customer-display session room | paired display device | display session | one display session | `/customer-display/*` |

Room names are server-derived and never on the wire (`stream` slot only). Authorization is re-validated on `AUTHORIZATION_CHANGED` (`authz-revalidation.ts`): a revoked session's stream closes.

**Not a realtime event (by design, Oct 20):** a refund whose processor answer was lost writes the audit row `pos_checkout_refund_status_unknown` and holds the row in `processing`; the POS refund panel reads `GET /pos/checkout/tickets/:id/refunds/unsettled` when the ticket is opened or any `payment_*` frame arrives. `payment_verifying` / `payment_recovered` frames exist today only for Manager Pay (`mobile-checkout.service.ts`, emitted through the checkout realtime port); `payment.unknown`, `payment.recovered`, `payment.refunded` and `payment.voided` are outbox events consumed by notifications / analytics but have no projection mapping yet — listed under B-21 follow-ups, not claimed.
