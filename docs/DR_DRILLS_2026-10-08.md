# DR_DRILLS_2026-10-08.md — disaster-recovery drill results

BUILD_PLAN Phase 11 (Constitution 4 §98, §148–151, §201 "Restore tested", "DR test completed where environment permits",
"Failure testing completed"). Four drills under `apps/api/scripts/drills/`, each run by hand on October 8, 2026 on the
development machine (PostgreSQL 16 on localhost, `redis-server` 7 installed, the API from `apps/api/dist`) while four
other build agents were working against the same PostgreSQL server. Output below is verbatim except that pino JSON
log lines are filtered out and one boot line is shortened (`…`).

**What these runs prove and what they do not.** They prove the CODE's behaviour: restore fidelity, lease recovery, pool
survival, Redis degradation. They do not prove the HOSTING: Railway's backup schedule, PITR, a restore from a real
production backup, or the time a real region failover takes — those are `docs/HOSTING_ACTIONS_FOR_KEVIN.md` A1–A5.

Every drill: one `PASS`/`FAIL` line per check, one final `DRILL <name>: PASS|FAIL` line, exit 0 only when all checks
pass, and cleanup of everything it started (child processes by their own PID, scratch databases `drill_*` dropped,
temporary files removed — the cleanup lines are in the output). Each drill was also run once with its property broken
from outside the drill (a wrapper on `PATH` or a `NODE_OPTIONS=--require` preload — no test switch inside the drill) and
FAILED, as it must; that log is at the end.

## 1. Restore — backup → restore → verify

706 tables, md5 over every payments and tickets row) are read inside that same snapshot — so the comparison is exact even
though other processes kept writing. The local database holds no encrypted rows, so the encryption round trip seals a
sentinel with this environment's webhook key into the SCRATCH copy and the platform verifier (`restore-verify.ts`) opens
it; against a production backup the verifier samples real rows instead. Restore time varies with machine load: 4.0 s on

## 3. Redis loss — first run FAIL (two defects), fixed in the tree, re-run PASS

Own `redis-server` (127.0.0.1:6391, no persistence), API with `REDIS_URL` and every Redis feature on
(`CACHE_STORE`, `RATE_LIMIT_STORE`, `LOGIN_THROTTLE_STORE`, `REALTIME_BUS` = `redis`), the salon owner signed in from
environment variables. Redis SIGKILLed, the same four requests repeated for 10 s, Redis started again.

**First run (unmodified code, 19:53 UTC): FAIL 11/13.** Two defects: (1) `POST /auth/login` answered **500** while Redis
was down (`RedisLoginThrottle` let every Redis error through); (2) each Redis command waited 2–6 s before failing
(`maxRetriesPerRequest: 2` + a growing `retryStrategy`), so a tenant-cache miss (`get`, `get`, `set`) took **10,001 ms**.

**Fixed by the lead at integration** (not a preload — in the repository): `packages/cache/src/redis.ts`
`withCommandTimeout()` gives every request/response command a 500 ms timeout (`REDIS_COMMAND_TIMEOUT_MS`; ioredis'
own `Command.setTimeout`), never the blocking / pub-sub commands (`subscribe`, `psubscribe`, `blpop`, `info`, …) which
legitimately wait — test `redis-command-timeout.test.ts`; `modules/identity/src/auth/login-throttle-redis.ts` fails OPEN
(no history, writes dropped, one warning a minute) — test in `login-throttle-redis.vitest.spec.ts`. Both tests were red
first; mutation checks in `scratchpad/p11/mut-lead.md`.

**Re-run after the fix: PASS 13/13** — during the outage every request kept its baseline status, the slowest request
2,009 ms (the cache miss: three commands × 500 ms + the real read), the API stayed up, and it reconnected and wrote keys
again 1.5 s after Redis returned:

## 4. Database failover — PostgreSQL stopped and started under load

Own scratch database `drill_failover`; the API with `PROCESS_ROLE=all` (today's deploy). Readiness probed every 100 ms
and a public request that queries the database every 250 ms, each with its own deadline. `service postgresql stop`, wait
for the first 503, `service postgresql start`. The database was unavailable 13.3 s end to end (stop + start of the
service; readiness answered 503 for 105 consecutive probes); the API process never exited, logged the discarded idle
connections, and readiness returned to 200 on its own. No request took longer than 78 ms — with the server down, a
connection is refused at once. (Note: the probe route's repository, `KyselyDisplayRepository.getSession`, swallows a query
error and answers "not found", so it answered 404 throughout; readiness is what shows the outage. A database error
reported as "not found" is a minor fail-soft defect worth fixing.)
