0. Execution Rules Before Coding
 • Inspect the real repository first. Reuse existing EMPLOYEE auth, refresh-token families, device-trust, Checkout, Payment,
  PaymentIntent, realtime, audit and provider abstractions wherever they already exist.
 • Do not create TapToPayAuthV2, PaymentDeviceV2, PaymentsV2 or a second Checkout authority beside working domains.
 • Never store salon passwords on the phone. Never store provider server secrets in the mobile app.
 • Never let the mobile app authoritatively choose tenant, branch, merchant configuration, final checkout amount or payment
  result.
 • Never call an unknown processor result declined. Never blind-retry a payment whose processor state is uncertain.
 • PostgreSQL remains authoritative business truth. Realtime is delivery, not payment truth.
 • Every sensitive operation must be attributable to tenant, branch, employee, device, session, checkout and payment
  transaction.

2. Password and Token Rules
 • Never persist employee/owner passwords or PIN plaintext on device.
 • Issue short-lived access tokens using the existing auth architecture; 5-15 minutes is a reasonable target only if compatible
      with current policy.
 • Use rotating refresh-token families with reuse detection, expiration, revocation and device association.
 • If a rotated refresh token is reused, trigger the existing token-family security response and revoke as policy requires.
 • On iOS store reusable authentication material only in Keychain; use Secure Enclave where appropriate for device-held
      private keys. On Android use Android Keystore if a supported Android payment app exists.

29. Do Not Trust Mobile "Approved"
The phone may report SDK success, but authoritative payment state belongs to backend + provider result/webhook/inquiry.
Mobile UI is presentation, not financial truth.

30. Stable Idempotency
 • One logical payment gets one durable idempotency identity.
 • Never construct an idempotency key from Date.now() or a new random value on every retry.
 • Repeated Pay taps for the same logical intent must produce one processor effect according to provider semantics.

32. Tip and Split Tender
If tip is chosen on mobile, backend recalculates the authoritative balance. For split tender, phone receives only the remaining
amount. Example: Checkout $200, POS cash $50, Tap to Pay request $150. Phone cannot charge $200.

 Critical anti-double-charge rule
 If the processor may already have received the charge, AI PowerSalon blocks a new conflicting tender until the original
 attempt is reconciled.



34. Unsettled-Tender Guard
Before starting a new Tap to Pay, card, cash override, gift card, wallet or other conflicting tender, inspect all relevant
unresolved sources: payments, payment_attempts, app/mobile payment intents and active processor attempts.

 YES → BLOCK conflicting tender
 NO → continue

  • Use bounded retry and backoff.

37. Verify Does Not Re-Charge

PART XII - Payment Data Security, Privacy and Logging

PART XVI - Mandatory Security, Concurrency and Multi-Device
Tests
59. Tenant Isolation
Tenant A device requests Tenant B checkout -> NOT FOUND / DENIED with no metadata leakage.

60. Branch Isolation
Branch A-only device requests Branch B checkout -> DENIED.

61. Revoked Device
Refresh, checkout list, claim, payment and refund from revoked phone -> all denied.

62. Multiple Devices
Register Phone A/B/C for same salon; unique IDs, sessions, keypairs, audit histories and independent revocation.

63. Same Checkout Concurrency
Phone A and B claim simultaneously -> one succeeds, one CHECKOUT_ALREADY_CLAIMED.

64. POS vs Phone Concurrency
Phone processing; POS attempts another card -> blocked. POS card processing; phone attempts -> blocked.

65. Split Tender
Checkout $200, POS cash $50, mobile receives $150 and cannot charge $200.

66. Checkout Mutation
Claim at version 7 / $150, POS edits to version 8 / $165 -> old request stale.

67. Refund Security
Unauthorized receptionist denied; manager with stale step-up gets STEP_UP_REQUIRED; manager after step-up allowed.

68. Store Switch
Unauthorized branch switch denied; authorized multi-branch switch requires permission + step-up + merchant refresh + audit.

69. Refresh Reuse
Reuse old rotated refresh token -> TOKEN_REUSE_DETECTED and session-family response.

70. Pairing Replay
Reuse pairing QR/token -> invalid/already used. Expired token -> denied.

71. Device Key Mismatch
Valid user token from wrong device key/signature -> sensitive request denied.

72. Realtime Revocation Failure
Disconnect realtime, revoke phone, next API request still denied.

73. Unknown Payment
Processor receives charge, network drops -> PAYMENT_STATUS_UNKNOWN, no second charge, Verify reconciles.

74. Logging Security
Search logs for PAN/CVV/passwords/refresh tokens/provider secrets/Auth headers -> none.

75. Audit Completeness
Full journey traces login -> session -> claim -> intent -> provider result -> checkout completion -> receipt.
