Built from four guides: *Stock Alerts* (two identical copies, incl. the Technician Usage guide), *Transactions* and *Payments & Money*.
Routes: `/tenant/inventory/alerts`, `/tenant/payments/transactions`, `/tenant/payments/overview` (Front Desk POS, EN + VI).

The page counted persisted `inventory_alerts` rows, which are only written when a product **crosses** a threshold — a product that was already low when it was set up never got a row. | Payments & Money: Revenue / Collections **$116.43** next to tenders summing **$168.15** | `overview()` summed only status `approved`: $63.16 + $53.27 = $116.43; the split's `partial` $51.72 tender (confirmed money) was dropped. ## Definitions (on the screens, in the APIs and in the CSV headers)

**Stock Alerts** — one scope, `modules/inventory/src/stock-alert-state.ts`, read by the page **and** the sidebar badge:
active, un-archived product × this location, location overrides applied, no stock row = 0 on hand, a product with no reorder level never alerts; severity exactly as `stockStatus()` (out ≤ 0; critical ≤ critical level, else ⌈reorder ÷ 2⌉; low ≤ reorder). **Open Alerts** = those not acknowledged in their current episode. `inventory_alerts` rows keep only the workflow (since / acknowledged by / resolved).
**Last Used By** = the latest *effective* use by `occurred_at DESC, id DESC` (usage ledger after corrections, plus Service-Done recipe deductions attributed to the ticket line's technician); never `updated_at`; "No recorded use" when none; other consumption is "Unknown / Historical".

**Transactions** — one row per tender (a payments row that is a real attempt; refund / void reversal rows are not tenders).
Transactions = confirmed tenders · Gross = Σ confirmed tender amounts (tips included — Checkout charges them in the amount) · Tips = the ticket's tip once per ticket · Net = Gross − completed refunds (pending refunds reserve, not subtracted). Date basis: Payment completed (default) · Created · Refunded. KPIs over every matching tender; the status filter narrows the list, never the money.

**Payments & Money** — every figure states its scope:
*Period* (preset / custom, salon time zone): Revenue = Σ (subtotal − discount) of tickets **paid** in the period (no tax, no tips; a partly paid ticket becomes revenue when paid) · Collections = confirmed tenders (= Transactions Gross; gift-card part shown) · Refunds Issued = completed refunds by refund date (pending shown apart) · Total Transactions = confirmed tenders · Average Ticket = Revenue ÷ paid tickets · Failed = declined / failed attempts (unresolved ones separate, never "failed").
*As of now*: Outstanding = partly paid tickets (total − confirmed tenders) + sent / partially paid invoices (total − recorded invoice payments) · Pending Payouts = processor settlements `pending` (expected money, never "in the bank").
*All time* (the six totals): same definitions; Total Payouts = processor payouts `settled` / `posted` (staff payroll is a separate ledger).

The photo reconciled: Today → Collections **$168.15**, Revenue **$108.83** (the two paid tickets' sales), Outstanding includes the split ticket's remaining **$30.00**; Transactions → **3 · $168.15 · $9.60 · $168.15**.

## Writes, schema and permissions

* Migration **716** (expand-only, idempotent): `product_usage_events` (quantity in integer hundredths, `occurred_at` vs `created_at`, source, on-behalf reason, idempotency key unique per tenant, consumed bottles, stock before / after), `product_usage_adjustments` (signed delta + reason, never an edit), a unique partial index so a usage event / adjustment can have exactly **one** stock movement, an alerts list index. Ownership registry updated.
* `InventoryService.recordProductUsage` / `adjustProductUsage` — one transaction under the product's stock-row lock: idempotency check → bottles `FOR UPDATE` → allocation (named bottle, low, opened least-left, sealed oldest; `product-usage-core.ts`) → bottle updates → recompute (alerts) → event → ONE `technician_usage` / `usage_correction` movement with the hundredths in `metadata_json` → audit. More than stock → 409 `USAGE_EXCEEDS_STOCK` unless the product allows negative stock (shortfall kept). Corrections restore the bottles the use came from (shortfall first).
* Routes: `tenant/inventory/stock-alerts/{summary,active,active/:productId/acknowledge,history,usage,usage/products/:id,technicians,pickers,events/:id,export}` (inventory.view; export inventory.reports.view), `POST …/usage` (inventory.product_usage.submit, `@Idempotent`), `POST …/usage/:eventId/adjustments` (inventory.stock.adjust, `@Idempotent`), `POST technician/inventory/usage` (own use only); `pos/payments/transactions/{list,summary,technicians,:paymentId,export}` (pos.checkout.view; export pos.reports.export); `pos/payments/money/{overview,services,payouts,search}` (pos.reports.view). ## Not verified / open

* TypeScript type checking and the POS vitest files could not run here (no node_modules); the five rewritten POS tests and the controller-reflection body specs need a CI run. The POS bundle builds (esbuild) and runs in the E2E.
* The harness calls controller methods directly: Nest guards, `@ListQuery`, the `@Idempotent` interceptor and body schemas are not exercised (the writer's own per-tenant idempotency key is).
* Record Product Use takes the time from the device clock (`datetime-local`) — correct on a POS in the salon; the optional service-ticket link is in the API but not in the dialog.
* "Alert Settings" opens the inventory product list (thresholds are per product and per location); there is no separate alert-settings screen.
* Settlement links only where `payments.settlement_batch_id` is set; bank confirmation only where `actual_deposit_date` is recorded. Chargebacks are read from `chargebacks` as recorded; no provider API was called.
