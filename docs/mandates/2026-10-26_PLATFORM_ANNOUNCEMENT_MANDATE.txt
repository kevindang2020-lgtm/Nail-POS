1. Platform Domain & Lifecycle
1. Primary product goal. Super Admin can publish a platform message that active matching POS clients receive without
refresh, logout, restart or redeploy.
2. No hard-coded banner. Announcement content must be backend-driven and editable without code deployment.
3. Repository audit first. Inspect shared POS header, search, notifications, platform admin, tenant/branch context, events,
outbox, realtime, permissions and audit before adding code.
4. Reuse existing infrastructure. If NotificationService, BroadcastService, PlatformNotificationService or SystemAlertService
already owns this responsibility, merge/upgrade it instead of creating a parallel system.
5. Product naming. Use Platform Announcements as the primary product/domain name.
6. Platform-only publisher. Only authorized platform/Super Admin identities can create/publish platform announcements.
7. Separate platform vs tenant security. Publishing originates from the PLATFORM realm. Salon Owners/Managers do not
get global platform-publish authority.
8. Audience modes. Minimum audience modes: ALL_TENANTS, SELECTED_TENANTS, SELECTED_BRANCHES. Future groups
may include plan/feature/environment targeting.
9. All-tenant use case. A platform maintenance/update message can reach every eligible POS.
10. Selected tenant use case. A tenant-specific support/payment/onboarding message reaches only the selected tenant.
11. Selected branch use case. A branch-specific operational message reaches only the selected branch.
12. Announcement entity. Persist message, optional title, type, priority, status, audience, schedule, dismissibility,
acknowledgement requirement, platform actors, timestamps and version.
13. Target entity. Normalize selected target records rather than storing arbitrary client-supplied strings.
14. Status lifecycle. Use DRAFT, SCHEDULED, ACTIVE, PAUSED, EXPIRED and ARCHIVED.
15. Draft rule. Drafts are visible only to authorized platform users and never render on POS.
16. Scheduled rule. Future start/end times are evaluated server-side using authoritative time.
17. Active rule. Only active and target-eligible announcements render on POS.
18. Paused rule. Pause hides an announcement without deleting it.
19. Expired rule. Expired history remains retained and auditable.
20. Archive rule. Archive published history instead of hard deleting it.

2. POS Top-Bar UX & Message Behavior
21. Announcement types. Support INFO, UPDATE, MAINTENANCE, WARNING and URGENT.
22. Visual severity. Normal/Update use subtle or gold treatment; Maintenance/Warning use amber; Urgent uses strong red
accent, consistent with the AI PowerSalon design system.
23. Exact top-bar placement. Insert the shared announcement region after Global Search/Search button and before
Date/Time/Notifications/Messages/Owner.
24. Header layout. Model top bar as left salon context, center-left search, flexible center announcement, and right utilities.
25. Responsive priority. Critical announcement and right-side account controls remain usable; search may shrink within
reasonable minimums.
26. Announcement width. Use flex/grid, not hard-coded coordinates. Prefer a flexible center width suited to current design
tokens.
27. Long-message wrapping. Long text must wrap naturally to a second line. Do not use a marquee.
28. Maximum inline height. Normally one line; allow two lines; beyond that clamp and expose More.
29. More behavior. More opens a popover/modal/drawer containing full text without navigating away from the current POS
workflow.
30. Short-message behavior. Short messages stay one line and compact.
31. Long-message behavior. Long normal messages may occupy two lines without overlapping content.
32. Very-long behavior. Very long text clamps to two lines plus More/full detail.
33. Optional title. Allow title but keep top-bar rendering compact, e.g. 'Maintenance: ...'.
34. Icon. Use existing icon library for type/severity rather than inconsistent emoji in production.
35. Dismissibility. Super Admin controls whether the announcement is dismissible.
36. Normal dismissal. Routine update/info messages may be dismissible.
37. Urgent persistence. High/urgent incidents may be non-dismissible.
38. Per-user dismissal. Dismissal affects that user/session policy, not every tenant user.
39. Acknowledgement mode. Optional requiresAcknowledgement shows an I Understand action and records
acknowledgement.
40. Non-blocking default. Routine announcements never block Check-In, Booking, Queue, Checkout or Payments.
41. Critical incident mode. Critical notices can be visually prominent but must not disable unrelated safe POS functions by
default.
42. Multiple active announcements. Do not stack many vertical banners. Show the highest-priority item with a compact
indicator/view-all pattern.
43. Priority order. Use deterministic LOW/NORMAL/HIGH/CRITICAL ordering.
44. Rotation. Equal-priority normal messages may rotate at a readable interval; CRITICAL remains pinned.
45. No marquee. Never use fast horizontally scrolling ticker text.
46. Hover/focus behavior. Pause optional rotation while hovered/focused.
47. Expanded behavior. Do not rotate the active item while its full message is open.

48. Super Admin create screen. Build Platform Announcements > New Announcement.
49. Safe message editor. Phase 1 uses plain text with line breaks; no arbitrary HTML/JS/iframes/CSS.
50. Character limit. Enforce a backend message length limit appropriate to existing conventions, e.g. about 2,000 characters.
51. Preview. Show Desktop POS preview before publish.
52. Preview widths. Preview standard desktop and smaller desktop/laptop behavior.
53. Audience UI. Use All Tenants / Selected Tenants / Selected Branches choices.
54. Tenant selector. Use server-side searchable/paginated tenant selection for large platform scale.
55. Branch selector. Branch selection follows tenant selection and uses authoritative branch data.
56. Publish now. Server sets startsAt using authoritative current time.
57. Schedule. Allow future start date/time.
58. Expiration. Support no-expiration or explicit end time; maintenance should normally expire.
59. Stale-message prevention. Do not leave old maintenance messages active days later.
60. Super Admin list. List message, type, priority, audience, status, starts, ends, creator and updated time.
61. Optimistic editing. Use versioning to prevent simultaneous platform-admin overwrite.
62. Version conflict. Return PLATFORM_ANNOUNCEMENT_VERSION_CONFLICT on stale writes.
63. Audit. Audit create/edit/publish/pause/resume/audience/priority/schedule/archive with actor, before/after, time and
correlation.

4. Realtime Delivery, Targeting & Shared Header
64. Realtime architecture. Publish through API -> domain -> PostgreSQL commit -> outbox/event -> realtime projection ->
matching POS clients.
65. Event naming. Use current event conventions, e.g. platform.announcement.published/changed.
66. Client-safe payload. Send only id/title/message/type/priority/dismissibility/ack requirement/schedule/version, not
platform-admin metadata.
67. Server-side targeting. Server decides recipients. Never broadcast all target lists to every POS and rely on client filtering.
68. Tenant isolation. A Tenant A-only message must never reach Tenant B via API, realtime, cache or logs.
69. Branch isolation. A Branch 1-only message must not reach Branch 2 unless explicitly included.
70. All-tenant fanout. All-tenants broadcasts reach every eligible active tenant POS.
71. Startup snapshot. POS fetches active announcements on load; do not rely on realtime history alone.
72. Snapshot + stream. Fetch snapshot, render, then subscribe; accept only newer versions.
73. Reconnect. On reconnect refetch authoritative snapshot and resume events.
74. Safety sync. Participate in the existing silent background reconciliation; never full-page refresh.
75. No header flicker. Update announcement state without reloading or flashing the whole top bar.
76. Layout stability. Reserve only needed announcement space; collapse naturally when no message exists.
77. Height transition. One-to-two-line change may smoothly adjust header height without overlap.
78. POS screen fit. No horizontal overflow or content collision.
79. All POS pages. Announcement appears on every authenticated POS page that uses the shared header.
80. Shared component. Implement once in the shared POS layout/header, not duplicated per route.

5. API, Security, Performance & Future Extensibility
81. Future app support. Architecture may later support Owner/Technician/Customer apps without exposing internal notices
to customers by default.
82. Surface targeting future. Potential surfaces: POS, OWNER_APP, TECHNICIAN_APP, CUSTOMER_APP, SUPER_ADMIN.
83. POS default. Current task defaults target surface to POS.
84. System-status integration future. System Status may prefill/suggest announcements, but auto-publish only if a deliberate
policy exists.
85. Platform APIs. Provide platform CRUD/publish/pause/archive endpoints under the existing platform namespace.
86. Platform realm. Mutation APIs require PLATFORM authentication.
87. POS read security. Active-announcement reads use EMPLOYEE realm plus trusted tenant/branch context.
88. Never trust tenant query. Resolve tenant/branch from authenticated trusted context, not arbitrary query/body tenant IDs.
89. Sanitization. Normalize line endings, remove unsupported control characters and reject unsafe markup.
90. XSS protection. Render escaped text; do not use uncontrolled dangerouslySetInnerHTML.
91. Links. Phase 1 may omit links; if later allowed, validate schemes and destinations.
92. Error taxonomy. Standardize not-found/access-denied/invalid-audience/invalid-schedule/version-conflict/already-
archived errors.
93. Schedule validation. Reject endsAt earlier than startsAt.
94. Empty message rejection. Trim and reject empty/whitespace-only announcements.
95. Idempotent publish. Repeated Publish actions produce one logical state transition.
96. Version field. Use version for stale-write prevention and client update ordering.
97. Performance. Use initial fetch + realtime + safety sync; no one-request-per-second polling.
98. Indexes. Review status/start/end/audience/target/published indexes based on actual query plans.
99. Caching. Short-lived cache may help but PostgreSQL remains authoritative.
100. Redis role. Redis may assist cache/fanout; never hold the only copy of an active announcement.
101. Scheduler discipline. If activation/expiration needs a scheduler, use one controlled scheduler rather than duplicate cron
effects across replicas.
102. Simpler schedule evaluation. If queries can reliably calculate active status from startsAt/endsAt, prefer that over
unnecessary mutation jobs.
103. Time handling. Store timestamps consistently and render admin schedule in the appropriate platform/admin timezone.
104. Localization future. Design for future English/Vietnamese variants without blocking Phase 1.
105. Localized data model. Follow existing localization architecture rather than prematurely hard-coding
message_en/message_vi.
106. Accessibility. Support keyboard, focus, screen reader labels, contrast, reduced motion and readable text.

Detailed POS Rendering Logic
ON POS LOAD:
 1. Authenticate employee.
 2. Resolve trusted tenant + branch.
 3. GET active announcement snapshot.
 4. Render highest-priority eligible message.
 5. Subscribe to authorized realtime updates.
 6. Ignore stale versions.
 7. On reconnect, refetch snapshot.


RENDER:
 - 1 line when short.
