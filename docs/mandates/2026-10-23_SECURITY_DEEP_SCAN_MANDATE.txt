Security reality

privilege, rapid detection, independent revocation, secure recovery and containment even if one security layer fails.

1. Security Program, Attack Surface & Threat Model
1. Security scope. Audit POS Web, Super Admin, API, Owner App, Technician App, Customer App, Online Booking, Customer Display,
Payment App, workers, realtime, database, migrations, scripts, CI/CD, containers, cloud configuration and third-party integrations.
2. Security baseline. Use OWASP ASVS 5.0, OWASP Top 10 2025, OWASP API Security guidance, NIST SSDF and applicable PCI-aligned
payment practices as verification baselines, not paperwork-only checklists.
3. Attack-surface inventory. Create SECURITY_ATTACK_SURFACE.md with every public/protected route, webhook, upload, WebSocket
channel, worker, scheduler, admin surface, database connection and external integration, including auth, scope, rate limit and risk
classification.
4. Threat model. Model anonymous attackers, credential stuffing, malicious customers, malicious employees/managers, stolen
devices/sessions, compromised owners/Super Admins, malicious dependencies, compromised CI credentials and cloud/database
insiders.
5. Crown-jewel assets. Treat Super Admin, platform credentials, merchant configuration, payment authority, payroll,
customer/technician PII, provider secrets, refresh tokens, device identities, audit records and production infrastructure as highest-value
assets.
6. P0 classification. Remote code execution, Super Admin takeover, auth bypass, cross-tenant access, payment manipulation, database

7. No report-only completion. Claude must not stop after finding vulnerabilities; internally fixable findings require code/config fixes,
regression tests and retesting before completion.
8. Safe testing. Run active security testing only in local/development/staging or dedicated security environments, not destructively
against production.

2. Backdoor, Malware, Persistence & Supply Risk
9. Suspicious-code scan. Search for eval, Function constructors, child_process, exec/spawn/shell calls, runtime downloads, base64/hex
obfuscation, reverse-shell patterns, crypto-mining code, hard-coded outbound sockets and unexplained network egress.
10. Startup/persistence scan. Inspect npm lifecycle scripts, package.json, Docker entrypoints, PM2/systemd/cron, CI scripts, Git hooks,
startup shell scripts, cloud user-data, serverless initialization and scheduled workers for unexpected persistence.
11. Hidden privilege paths. Audit every code path that creates platform users, owners, roles, permissions, tokens, invitations,
password resets, impersonation or MFA bypass for proper authorization and audit.
12. Outbound destination inventory. Enumerate expected outbound providers and flag unknown domains/IPs, tunnels, paste sites,
unapproved file hosts or analytics endpoints.
13. Dependency malware scan. Audit lockfiles, native/mobile dependencies, Git dependencies, Docker images and GitHub Actions for
vulnerabilities, typosquatting, abandoned packages, dangerous install scripts and unexpected binary downloads.
14. SBOM. Generate an SBOM for backend, frontend, mobile and containers, including package/version/source/license and current
security status.
15. Malware finding standard. For suspicious code report FOUND, NOT FOUND or SUSPICIOUS/REQUIRES REVIEW with file paths and
evidence; never claim malware-free merely because a source scan passed.
16. Developer-machine risk. If prior developer-machine compromise is suspected, require clean rebuild plus credential/key rotation
rather than trusting only malware removal.

6. Authentication & Session Security
49. Authentication realms. Keep EMPLOYEE, PLATFORM, CUSTOMER, PUBLIC_BOOKING, SERVICE and INTEGRATION realms strictly
separated.
50. Super Admin MFA. Require MFA for all production Super Admin/platform accounts with no normal opt-out.
51. Password storage. Use a current strong one-way password hashing algorithm and safe parameters; never plaintext or reversible
passwords.
52. Access tokens. Use short-lived access tokens consistent with the existing architecture; do not grant long-lived bearer
payment/admin authority.
53. Refresh rotation. Use rotating refresh-token families with expiration, device/session association and reuse detection.
54. Refresh-token reuse. A reused rotated refresh token must trigger the configured family/session security response and audit alert.
55. Logout. Logout invalidates the server-side refresh session/family, not only local storage.
56. Remote session revocation. Owners/platform admins can revoke appropriate sessions/devices; revocation is enforced server-side.
57. Employment termination. Terminated/disabled employees promptly lose POS, queue, payment and session authority.
58. Credential stuffing. Protect login with rate limits, progressive response controls, MFA and security alerts without making attacker-
triggered permanent lockout easy.
59. Step-up authentication. Require fresh authentication for merchant changes, refunds, role/permission changes, new platform
admins, Support Mode, device revocation, payment/security settings and other high-risk actions.
60. Step-up freshness. Enforce a bounded freshness window and server-side proof rather than a frontend-only timer.
61. Super Admin sessions. Provide session/device visibility, last activity and revocation for platform accounts.
62. Biometric boundary. If mobile biometrics are used, OS biometrics unlock device-bound credentials; backend never stores
biometric templates.
63. Session expiry in realtime. Expired/revoked sessions stop receiving realtime data and cannot continue authorization through an
existing WebSocket connection.
64. Service credentials. Service/integration identities use separate credentials/scopes from human accounts and minimal permissions.
65. Account recovery. Audit password reset/account recovery for enumeration resistance, token expiry, single use and audit logging.
66. Security notifications. Notify appropriate owners/platform operators about high-risk login/session events without leaking secrets.

7. Authorization, Tenant & Branch Isolation
67. Frontend is not authority. Hiding a button is UX only; every privileged operation is authorized on the backend.
68. RBAC plus scope. Use RBAC + resource scope + policy conditions with OWN, ASSIGNED, BRANCH, SELECTED_BRANCHES, TENANT
and PLATFORM as applicable.
69. Mass-assignment defense. Audit direct object spreading/body-to-entity updates; clients cannot set tenantId, platformAdmin, role,
permissions, merchantId, approved/paid status or other privileged fields unless explicitly authorized.
70. Super Admin escalation tests. Attempt tenant/admin roles against platform routes, platform users, billing, tenant management,
merchant configuration and Support Mode; expect denial without explicit platform authority.
71. Tenant isolation P0. Tenant A must never read or mutate Tenant B customers, appointments, employees, payments, payroll,
receipts, inventory, memberships, messages, devices or reports.
72. Server-derived tenant. Do not trust req.body.tenantId, query tenantId or a custom tenant header as authority without
authenticated verification.
73. Scoped repositories. Tenant-owned repository queries require trusted tenant scope so object IDs cannot be used across tenants.
74. IDOR tests. Systematically substitute IDs across customers, appointments, employees, payments, payroll, receipts, expenses,
inventory, gift cards, memberships, messages, devices and reports.
75. Branch isolation. Repeat equivalent tests for branch-scoped resources and manager access.
76. Support Mode. Platform support access to tenant-private data requires explicit reason, tenant/scope, expiration and tamper-
resistant audit.
77. Cross-tenant exports. Exports and report jobs must re-enforce tenant/branch scope, including background-worker execution.
78. Worker isolation. Background jobs carry trusted tenant context and cannot process arbitrary tenant IDs supplied by untrusted
clients.
79. File isolation. Signed file URLs/object access must enforce tenant ownership and expire appropriately.
80. AI isolation. AI processing must receive only data permitted for the active tenant/branch and must not cross-contaminate tenant
prompts/context.
81. Cache isolation. Cache keys include tenant/branch scope where relevant to prevent cross-tenant collisions.
82. Realtime isolation. Realtime channels/subscriptions are authorized server-side, not trusted from client channel names.

8. Injection, Browser & Request Security
83. SQL injection. Use parameterized Kysely queries; audit raw SQL/sql.raw/string concatenation and unsafe dynamic identifiers.
84. Dynamic sorting. Whitelist sort columns and direction; never concatenate arbitrary client expressions into SQL.
85. DB privileges. Application database user must not run as PostgreSQL superuser and should have only required privileges.
86. Database TLS. Use encrypted DB connections where appropriate for deployed topology.
87. XSS audit. Search dangerouslySetInnerHTML, innerHTML, rich text, markdown renderers, notes and announcement rendering for
unsafe execution.
88. Output escaping. Treat customer, employee and platform-entered content as untrusted and render safely.
89. CSP. Deploy a strict practical Content Security Policy and remove unsafe-inline/unsafe-eval where possible.
90. CSRF. If cookies carry authentication, implement robust CSRF defenses; review browser credential behavior even with bearer
tokens.
91. SSRF audit. Audit every server-side URL fetch influenced by users, including receipt/image imports, webhook testers, AI fetches and
integration setup.
92. SSRF private ranges. Block attacker-controlled access to localhost, RFC1918/private ranges, link-local/cloud metadata and internal
service hostnames unless explicitly required.
93. Egress allowlist. Where practical, restrict high-risk server egress to approved destinations such as Fiserv, Twilio, AWS, SendGrid
and approved AI providers.
94. Command injection. Audit exec/spawn/shell usage and never pass untrusted user values through a shell.
95. Dynamic code. Remove unnecessary eval/Function usage, especially around untrusted input.
96. Template injection. Audit server/client templating and report-generation paths for unsafe expression execution.
97. Path traversal. Validate filesystem/object keys; never derive server paths directly from user-supplied filenames.
98. Open redirects. Validate redirect/return URLs used in auth, booking or integrations.
99. Header injection. Sanitize values written into response headers, filenames and content-disposition.
100. Prototype pollution. Audit unsafe object merges and dependency exposure to prototype pollution.
101. Deserialization. Avoid unsafe deserialization of untrusted objects or provider payloads.

9. Upload, Webhook & Realtime Security
102. Hostile upload model. Treat receipts, portfolio images, ads, documents and avatars as hostile until validated.
103. Upload validation. Validate extension, MIME, magic bytes, size, ownership and supported format.
104. Quarantine. Upload -> quarantine -> malware scan -> clean -> process; unscanned documents are never treated as trusted.
105. Object storage. Use private bucket/container, randomized keys, encryption, signed URLs with short TTL and tenant-safe

106. Malware scanner failure. If malware scanning is unavailable, keep the file quarantined rather than assuming it is clean.
107. Webhook authenticity. Verify provider-supported signatures/authentication for Fiserv/CardPointe, Clover, Twilio and every

108. Webhook replay. Use timestamps/event IDs/idempotency/replay checks where supported.
109. Webhook tenant resolution. Resolve tenant through trusted merchant/provider configuration, not attacker-controlled payload

110. Webhook schemas. Strictly validate webhook payload shape and reject unexpected types/fields where appropriate.
111. Realtime auth. Authenticate every WebSocket/realtime connection.
112. Realtime subscription auth. Authorize subscriptions server-side against trusted tenant/branch scope.
113. Realtime event validation. Validate inbound client events; never allow a client to forge server-authoritative business events.
114. Realtime revocation. Revoked/expired sessions must lose realtime access even if the socket remains open until the server closes it.
115. Realtime payload minimization. Send only the data required for the subscriber surface; avoid leaking other tenants or
unnecessary PII.
116. Reconnect safety. On reconnect, fetch authorized snapshots and resume newer events without exposing stale/unauthorized state.

117. Payment high-risk review. Deep-audit CardPointe, Fiserv, Clover, Tap to Pay, wallet top-up, refunds, voids and split tender.

119. Merchant isolation. Merchant config is derived from trusted tenant + branch and cannot be selected by arbitrary client merchant

120. Stable idempotency. Financial retry identity is stable per logical intent; never use Date.now/random retry values that create a

123. Refund idempotency. Repeated refund/verify commands must not produce duplicate processor effects.

125. Provider secrets. Payment provider secrets remain server-side and never in POS/mobile bundles.
126. Webhook payment reconciliation. Processor webhooks are authenticated, idempotent and correlated to trusted merchant/intent
records.
127. Payment audit. Every payment/refund/void records tenant, branch, user, device where applicable, Checkout, intent and provider

128. Payment log scan. Security test searches logs/telemetry for PAN-like data, CVV, Authorization headers, provider keys and refresh

129. Wallet/top-up recovery. Unknown top-up results use stable intent + provider inquiry and credit the wallet exactly once.
